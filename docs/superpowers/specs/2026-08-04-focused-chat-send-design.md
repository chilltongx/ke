# “可”跟随当前焦点的跨应用发送设计

- 日期：2026-08-04
- 项目：可
- 平台：macOS
- 首批专用适配：Codex、Visual Studio Code、微信

## 1. 摘要

把“可”从只操作 Codex 的悬浮按钮改为跟随当前焦点的跨应用聊天发送工具。用户先在前台应用中
聚焦一个空聊天输入框，再点击不抢焦点的悬浮按钮；应用记录原前台进程、窗口和焦点元素，确认
目标属于聊天场景且仍为空后，输入一次“可”，重新校验目标未变化，最后向同一进程发送一次
Enter。

新版不再激活 Codex，也不寻找最近使用的 Codex 窗口。Codex、Visual Studio Code 和微信使用
专用识别规则；其他应用只在保守的通用规则能够确认聊天语义时才允许发送。任何目标、焦点或内容
状态不明确的情况都拒绝操作并闪红。

## 2. 已确认决策

- 采用混合识别：三个首批应用使用专用适配，其他应用使用保守的通用识别。
- 只操作用户点击前已经聚焦的输入框，不激活、切换或猜测其他应用和窗口。
- 只允许空白聊天输入框；已有草稿时拒绝，不覆盖也不追加。
- 代码编辑器、终端、搜索框、密码框和普通表单一律拒绝。
- 发送动作统一为向目标进程发送 Enter，不查找或点击“发送”按钮。
- 若目标应用把 Enter 配置为换行，本工具不会自动改用其他快捷键。
- 保留现有悬浮按钮、拖动、点击锁、绿色成功和红色失败反馈。

## 3. 目标与非目标

### 3.1 目标

- 在 Codex、Visual Studio Code 侧边栏聊天和微信消息输入框中实现一次点击发送“可”。
- 让其他具有可确认聊天语义的 macOS 应用也能使用同一流程。
- 以当前真实焦点作为唯一目标，不因点击悬浮按钮丢失或改变用户的输入位置。
- 在写入前和按 Enter 前重复校验目标，避免焦点竞争造成误输入或误提交。
- 延续已有 Codex 占位符兼容逻辑，避免空闲一段时间后把占位内容误判成草稿。

### 3.2 非目标

- 不覆盖、清空或追加到已有草稿。
- 不支持代码编辑器、终端、搜索框、密码框或普通表单。
- 不提供设置页面、应用白名单编辑器或自定义发送快捷键。
- 不保证所有未知应用都能被识别；证据不足时安全失败。
- 不判断消息是否已被服务器接收，也不因网络结果自动重试。
- 不改变周额度光环、安装方式、登录项或应用视觉设计。

## 4. 用户体验

### 4.1 成功路径

1. 用户在聊天应用中把光标放入一个空输入框。
2. 用户点击悬浮“可”。
3. 面板保持不激活，原应用和原输入框继续持有焦点。
4. 应用确认目标是空白聊天输入框并输入“可”。
5. 应用确认进程、窗口和焦点没有变化，然后向同一进程发送 Enter。
6. Enter 事件成功投递后，按钮显示现有绿色反馈。

绿色表示本地 Enter 事件已向经过校验的目标进程投递，不表示远端服务已确认收到消息。

### 4.2 拒绝路径

以下任一情况出现时立即停止并显示现有红色反馈：

- 没有 Accessibility 权限；
- 没有可确定的前台应用、焦点窗口或焦点元素；
- 焦点元素不可编辑、不是聊天输入框或属于明确拒绝的场景；
- 输入框已有非空白内容；
- 写入前或按 Enter 前，PID、窗口或焦点元素发生变化；
- 写入后无法确认输入框内容严格等于“可”；
- Enter 事件无法投递。

失败后不寻找第二个候选输入框，不切换应用，不自动重试。若“可”已经写入但后续校验失败，保留
现场供用户检查，不发送 Enter。

## 5. 系统架构

### 5.1 组件边界

运行时分为五个职责：

1. `ManualApprovalController`：保留点击锁和按钮反馈，只发起一次发送请求。
2. `FocusedTargetProvider`：同步获取点击时的前台 PID、Bundle ID、焦点窗口和焦点元素。
3. `ChatTargetClassifier`：通过专用适配或通用规则判断焦点元素是否为聊天输入框。
4. `FocusedInputClient`：读取、输入、重新校验目标，并向指定 PID 投递 Enter。
5. `FocusedChatApprovalSender`：编排安全门、写入确认和发送流程。

现有 `CurrentWindowApprovalSender` 的编排职责迁移到 `FocusedChatApprovalSender`。现有
`AccessibilityClient` 中可复用的 AX 遍历、值标准化和 PID 定向事件能力保留，但移除“激活
Codex”和“查找 Codex 发送按钮”在主流程中的依赖。

### 5.2 焦点快照

`FocusedTargetSnapshot` 至少包含：

- 目标 PID；
- Bundle ID；
- 焦点窗口引用；
- 焦点元素引用；
- 采集时的角色、子角色、可编辑状态和必要的上下文证据。

快照在点击处理开始时同步创建。后续每个破坏性步骤前，重新读取系统焦点并要求 PID、窗口和
元素身份与快照一致。若悬浮面板意外成为前台应用，或 AX 无法证明元素身份一致，则失败，不通过
相似标签重新定位。

### 5.3 聊天目标分类

分类器按以下顺序执行：

1. 通用硬拒绝：密码/安全输入、只读或禁用控件、搜索/查找、终端、源代码编辑器和普通表单。
2. 若 Bundle ID 有专用适配，只使用该适配裁决；专用适配拒绝后不得回退到通用规则。
3. 若没有专用适配，再使用保守的通用聊天规则。

专用适配初始覆盖：

- Codex：识别主对话区域的 composer，并保留空闲占位符归一化。
- Visual Studio Code：只接受聊天侧边栏或聊天编辑器中的消息 composer，拒绝代码编辑器、集成
  终端、命令面板、搜索和 SCM 输入框。
- 微信：只接受当前对话窗口的消息编辑区，拒绝联系人、聊天记录和全局搜索框。

通用规则只检查焦点元素及其有限祖先和相邻语义，不扫描或读取应用中的其他输入框。它要求元素
可编辑，并能从角色、描述、标题、祖先区域或相邻控件中得到明确的聊天/消息语义；明确的编辑器、
终端、搜索、账号、地址或表单语义具有否决权。无法形成唯一结论时返回“不支持”。

### 5.4 空内容规则

写入前读取焦点元素的当前值：

- `nil`、空字符串或仅包含空白和换行的值视为空；
- Codex 已知的占位符 Accessibility 伪值由 Codex 适配器归一化为空；
- 其他任何可见字符都视为已有草稿并拒绝；
- 无法可靠读取值时拒绝，不以选区长度或视觉占位文字猜测。

### 5.5 输入与发送

发送器固定执行以下状态机：

`捕获焦点 → 分类 → 校验为空 → 重验焦点 → 输入“可” → 确认值 → 重验焦点 → 投递 Enter`

- 文本和 Enter 都通过 PID 定向事件发送，不使用剪贴板。
- 每次点击最多输入一次“可”并投递一次 Enter。
- 写入后只有在值严格等于“可”时才允许继续。
- 不读取或点击发送按钮；发送按钮只能作为通用分类器的聊天语义证据之一。
- 不通过清空内容或再次输入来恢复失败。

## 6. 错误与日志

对外继续复用现有红色反馈和提示区域。内部错误类型至少区分：

- `accessibilityPermissionMissing`
- `frontmostTargetUnavailable`
- `focusedElementUnavailable`
- `unsupportedInputContext`
- `composerNotEmpty`
- `targetChanged`
- `textInsertionFailed`
- `insertedValueMismatch`
- `returnDeliveryFailed`

诊断日志只记录错误类型、Bundle ID、PID 和必要的 AX 角色信息，不记录输入框内容、聊天对象、
消息历史或窗口标题。已有草稿的具体文本不得写入日志。

## 7. 代码结构调整

- `AppDelegate`：把运行时发送器从 Codex 专用实现替换为焦点跟随实现；面板生命周期不变。
- `ApprovalSender`：保留现有无目标参数的接口，目标由点击时的系统焦点决定。
- `CurrentWindowApprovalSender`：由 `FocusedChatApprovalSender` 替代或重命名。
- `CurrentCodexAutomation`：拆出可复用的焦点、输入和事件能力；Codex 特例迁入适配器。
- `AccessibilityClient`：支持读取任意前台进程的焦点元素、有限上下文和元素身份重验。
- 新增 `ChatTargetAdapter` 协议及 Codex、Visual Studio Code、微信三个实现。
- 新增 `GenericChatTargetClassifier`，仅用于没有专用适配的 Bundle ID。
- README 与手动验证文档更新为“跟随当前空聊天框”，并明确 Enter 的行为限制。

实现时保持分类、AX 访问和发送编排可独立测试，避免把多应用判断堆叠在单个遍历函数中。

## 8. 测试策略

### 8.1 单元测试

- 空字符串、纯空白和换行允许继续；已有草稿拒绝且不写入。
- Codex 已知占位符归一化为空，其他未知伪值拒绝。
- PID、窗口或焦点元素在任一重验点变化时停止。
- 只有写入值严格等于“可”后才投递 Enter。
- 所有失败路径都不投递 Enter；单次点击最多投递一次。
- Codex composer 接受，Codex 搜索或非主对话输入拒绝。
- Visual Studio Code 聊天 composer 接受，代码编辑器、终端、搜索、SCM 和命令面板拒绝。
- 微信消息 composer 接受，联系人搜索、聊天记录搜索和普通搜索拒绝。
- 通用规则接受具有明确聊天语义的可编辑控件，拒绝普通表单、搜索、密码、编辑器和终端。
- 专用适配拒绝后不回退到通用规则。
- 日志不包含输入框原始值。

### 8.2 真实应用验收

- Codex 前台空 composer：输入并发送一次“可”。
- Codex 空闲一段时间后再次点击：占位符不会导致误报草稿。
- Visual Studio Code 侧边栏聊天获得焦点：输入并发送一次“可”。
- Visual Studio Code 代码编辑器、终端或搜索获得焦点：闪红且不产生输入。
- 微信当前对话消息框获得焦点：输入并发送一次“可”。
- 微信搜索框获得焦点：闪红且不产生输入。
- 三个应用中的输入框已有草稿：闪红，原内容不变。
- 点击过程中切换应用、窗口或焦点：停止并闪红。
- 一个未知聊天应用满足通用规则：输入并发送；证据不足时闪红。
- 目标应用把 Enter 配置为换行：投递 Enter，不改用其他发送方式。

真实验收使用测试会话，避免向真实联系人或生产频道误发消息。

## 9. 验收标准

- 悬浮按钮不激活自身，也不主动激活 Codex 或其他目标应用。
- 用户点击前聚焦的空聊天输入框是唯一允许操作的目标。
- Codex、Visual Studio Code 侧边栏聊天和微信消息框均可发送一次“可”。
- 代码编辑器、终端、搜索框、密码框和普通表单不会收到文字或 Enter。
- 已有草稿不会被覆盖、清空、追加或提交。
- 写入和发送前均验证同一 PID、窗口和焦点元素；变化时不发送 Enter。
- 每次点击最多写入一次“可”并向同一 PID 投递一次 Enter。
- 未知应用只有在通用规则确认聊天语义时才工作，否则安全失败。
- 闲置后再次点击不因 Codex 占位符或过期目标引用爆红。
- 现有拖动、点击锁、绿色/红色反馈和周额度显示不回归。

## 10. 风险与缓解

- Electron 和原生应用的 Accessibility 层级可能随版本变化：专用适配使用小范围结构证据并由
  夹具和真实应用测试覆盖；无法确认时拒绝。
- 通用分类可能出现误判：硬拒绝优先，未知结论默认拒绝，且已支持应用不得回退通用规则。
- 点击期间焦点可能发生竞争：在写入前和 Enter 前比较原始元素身份，不按标签重新搜索。
- 某些输入框不公开可靠的 AX 值：不降级为盲发，直接闪红。
- 某些应用把 Enter 设为换行：这是已确认的统一 Enter 策略；文档明确限制，不自动改用按钮或
  组合键。
- Enter 成功投递不等于网络发送成功：绿色只代表本地动作完成，不自动重试，避免重复消息。
- Accessibility 权限能力较高：只访问当前焦点及有限上下文，不记录消息内容，不使用剪贴板。
