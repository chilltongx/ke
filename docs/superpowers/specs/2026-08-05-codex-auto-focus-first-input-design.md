# Codex 无输入焦点时自动发送设计

- 日期：2026-08-05
- 项目：可
- 平台：macOS
- 范围：前台 Codex 窗口

## 1. 目标

用户从其他应用切回 Codex 后，即使消息输入框没有光标，也能点击悬浮“可”完成原有操作，
无需先手动点击输入框。

本功能只改变 macOS 版在前台 Codex 没有可编辑焦点时的目标定位方式。已经聚焦输入框的流程、
Visual Studio Code、微信和其他应用保持不变。

## 2. 已确认决策

- 只在前台应用 Bundle ID 为 `com.openai.codex` 时启用自动定位。
- 若系统已经报告一个可编辑输入框为焦点，继续使用现有分类和发送流程，不自动改选其他元素。
- 若当前焦点不存在，或焦点是不可编辑的窗口、容器或按钮，按 Accessibility 导航顺序扫描当前
  Codex 焦点窗口。
- 使用扫描到的第一个启用、值可写、角色为 `AXTextArea` 或 `AXTextField` 的元素。
- 自动定位阶段不要求候选具有聊天语义，也不要求窗口中只有一个候选。选中后仍经过现有 Codex
  分类器：具有明确搜索语义的输入框会被拒绝，但语义不完整的较早输入框仍可能被误选。这是用户
  明确选择的方案，已接受该风险。
- 仍要求目标内容为空。已有草稿时拒绝，不覆盖、不追加、不发送 Enter。
- 不缓存上次输入框，不切换应用，不扫描其他窗口。

## 3. 运行流程

点击后执行：

1. 确认 Accessibility 权限、前台 PID、Bundle ID 和焦点窗口。
2. 尝试读取当前焦点元素。
3. 若当前元素是启用且值可写的 `AXTextArea` 或 `AXTextField`，进入现有分类流程。
4. 否则，仅当 Bundle ID 为 `com.openai.codex` 时，广度优先扫描焦点窗口后代；子元素顺序沿用
   `AXChildren` 与 `AXChildrenInNavigationOrder` 合并后的顺序。
5. 选取第一个启用、值可写的 `AXTextArea` 或 `AXTextField`。
6. 将候选的 `AXFocused` 设为 `true`，随后重新读取系统焦点，要求它与候选相同。
7. 从该元素建立现有 `FocusedTargetSnapshot`，通过现有 Codex 分类器后读取并确认内容为空。
8. Codex/Electron 可能在获得焦点后重建输入框 Accessibility 对象。仅对本次自动聚焦目标，允许
   在写入前接受一次对象身份更新；PID、Bundle ID、窗口和完整聊天上下文必须与快照相同。对象
   一旦更新或文字写入成功，立即恢复严格对象身份校验。
9. 写入“可”，确认值严格等于“可”，再次验证前台应用、窗口和焦点元素，向同一 PID 投递
   Enter。

扫描最多检查 2,048 个元素。超过上限时停止并闪红，避免异常 Accessibility 树造成卡顿。

## 4. 组件调整

### `AccessibilitySystemProviding`

增加设置元素焦点的窄接口。系统实现只写入候选元素的 `kAXFocusedAttribute`，测试实现记录焦点
变化并允许模拟失败。

### `AccessibilityClient`

把当前焦点解析扩展为两段：

- 正常解析：沿用系统焦点与已聚焦后代兜底。
- Codex 自动定位：正常解析没有得到可编辑输入框时，扫描当前窗口并聚焦首个可编辑元素。

自动定位完成后必须重新读取系统焦点，不以“设置属性返回成功”代替焦点确认。自动聚焦快照可在
写入前接受一次等价的 Accessibility 对象替换，以兼容 Codex/Electron 聚焦后重建 composer。替换
必须保持 PID、Bundle ID、窗口和完整 `FocusedChatContext` 不变；对象一旦替换或文字写入成功，
后续重新验证继续要求同一对象。普通已聚焦目标不获得该额度。

### 其他组件

`FocusedChatApprovalSender`、`ChatTargetClassifier`、悬浮面板和反馈动画不改变职责。自动定位只在
目标捕获阶段发生。

## 5. 失败与反馈

以下情况沿用红色失败反馈，不写入文字、不发送 Enter：

- 前台应用不是 Codex，且没有有效焦点输入框；
- Codex 当前窗口没有可编辑输入元素；
- Accessibility 树读取失败或超过扫描上限；
- 候选无法获得焦点，或重读焦点后不是同一元素；
- 候选已有草稿；
- 聚焦后应用、窗口或输入框上下文发生变化；
- 自动聚焦输入框发生第二次 Accessibility 对象替换；
- 写入或 Enter 投递失败。

成功反馈仍表示本地 Enter 已投递，不表示远端消息已确认。

## 6. 测试

新增自动化测试：

- Codex 没有焦点元素时，扫描并聚焦首个可编辑输入框。
- Codex 当前焦点为窗口、容器或按钮时，使用首个可编辑输入框。
- 导航顺序中存在多个输入框时，严格选择第一个。
- 首个候选已有草稿时拒绝，不继续尝试第二个候选。
- 非 Codex 应用没有可编辑焦点时不扫描首个输入框。
- 已聚焦可编辑输入框时保持现有目标，不改选其他元素。
- 设置焦点失败或焦点确认不一致时停止。
- 扫描超过 2,048 个元素时停止。
- 自动聚焦后窗口、应用或元素变化时不发送 Enter。
- 自动聚焦后、写入前首次出现上下文相同的 Accessibility 对象替换时继续；第二次替换、上下文
  变化或写入后的替换均停止。
- 全量 `swift test` 和现有安装、签名、打包检查继续通过。

## 7. 手动验收

使用专门测试会话：

1. 从其他应用切回 Codex，不点击 composer，点击“可”，应输入并发送一次“可”。
2. Codex composer 已聚焦时，行为与当前版本相同。
3. Composer 有草稿时，不覆盖、不追加、不发送。
4. Codex 窗口含搜索框时，记录扫描顺序和分类结果；明确搜索语义应闪红，语义不完整候选仍属于
   已接受风险。
5. VS Code、微信无焦点时不启用本次 Codex 专用自动扫描。

## 8. 非目标

- 不为 Windows 版增加同类行为。
- 不为 VS Code、微信或通用聊天应用自动寻找输入框。
- 不通过坐标点击输入框。
- 不判断远端是否收到消息，不自动重试。
- 不新增设置页面或候选选择界面。
